# Spec-Driven Development workflow

Use this skill only when the change is complex enough to benefit from explicit
scope, requirements, design, and task traceability. Skip it for small fixes,
documentation, configuration, and mechanical edits — CLAUDE.md already says
trivial features get direct implementation.

The native OpenSpec artifacts are generated by OpenSpec itself. The repository
templates in `~/.claude/templates/` are retained for legacy compatibility; in
OpenSpec mode, `sdd-tasks.md` is the only one used as an additional task
contract and the other phase templates must not be copied into a second
`specs/` tree.

## Before starting

1. Read the project `CLAUDE.md`, README, architecture docs, and the relevant
   existing OpenSpec change/specs.
2. Run the project preflight and verify that CodeGraph is initialized before
   exploring implementation code. If it is missing, report `codegraph init`
   as a user-authorized setup step; do not silently initialize.
3. Identify the stack, test runner, deploy path, and relevant constraints.
4. This project's SDD workflow uses OpenSpec as its source of truth. Verify
   the CLI, `openspec/specs/`, `openspec/changes/`, and `openspec status --json`.
   If any check fails, stop SDD work and report the authorized setup step.
5. This project intentionally keeps OpenSpec artifacts local to avoid AI
   residue in Git. Verify that the root `.gitignore` ignores `openspec/` unless
   it was already tracked before the session. Do not stage or commit newly
   created OpenSpec artifacts without explicit user instruction.
6. Do not create local `specs/<feature-slug>/` artifacts as a parallel format.

## OpenSpec mode

OpenSpec is the agreement layer for this project's SDD workflow. It is not a
test runner or a replacement for CodeGraph. Its files stay local and ignored
by default in this project. Verify the CLI,
`openspec/specs/`, `openspec/changes/`, and `openspec status --json`, then use
the `automatic-task-orchestrator` skill and its CLI-level artifact sequence.
Generated `/opsx:*` commands are an explicit fallback, not a prerequisite for
automatic mode. In particular, do not use `/opsx:propose` as the automatic
planning primitive because OpenSpec 1.9.0 intentionally stops that command
after planning. If OpenSpec is not initialized, stop before creating proposals
or code and request authorization for the CLI install and `openspec init`;
never install or initialize it silently.

## Starting a change

After the preflight passes, the automatic route starts a change with
`openspec new change <safe-name> --json`, reads the artifact order from
`openspec status --change <name> --json`, and obtains each artifact's
instructions before writing it. OpenSpec owns the generated artifacts under
`openspec/changes/<change-name>/`; do not invoke the legacy local scaffolder
or create a second `specs/<feature-slug>/` tree. The explicit
`/opsx:propose` command remains available when the user intentionally wants a
planning-only turn.

The repository's task contract in `templates/sdd-tasks.md` remains an
additional execution gate. It does not replace OpenSpec's generated proposal,
spec delta, design, or task artifacts.

## Phases

### 1. Explore -> Proposal (automatic CLI route; explicit `/opsx:propose` fallback)

- State the problem in one sentence.
- Record scope in and out.
- Inspect existing patterns and affected modules.
- Consider at least two viable alternatives when the decision is architectural.
- Record assumptions and unresolved questions.
- Write the proposal at the path returned by OpenSpec to
  `openspec/changes/<change-name>/proposal.md`.

**Decision gate.** In a clear user-authorized oneshot, continue automatically
after the proposal. Pause only for an unresolved scope, security, destructive
or external-side-effect decision; generated artifacts do not require
ceremonial approval.

### 2. Requirements -> Spec deltas

- Write independently testable requirements and scenarios in the generated
  `openspec/changes/<change-name>/specs/` deltas.
- Keep user stories with priorities (P1/P2/P3) when they improve traceability.
- Express observable acceptance scenarios in Given/When/Then form when useful.
- Give each functional requirement a stable `FR-###` identifier.
- Define edge cases, non-functional constraints, success criteria, out of scope.
- Resolve `[NEEDS CLARIFICATION]` before implementation, or document the bounded
  assumption explicitly.

### 3. Design (`design.md`, when needed)

- Map concrete files, modules, data flow, boundaries, dependencies, risks, rollback.
- Reuse the repository's existing architecture unless the proposal justifies a change.
- Record rejected alternatives and the reason for rejection.
- Re-check security, performance, accessibility, privacy, and operational impact.
- Keep the technical approach in the generated
  `openspec/changes/<change-name>/design.md` when the change needs one.

**Decision gate.** Requirements + design must be internally consistent before
implementation. Ask the user only if a material decision remains unresolved;
otherwise continue automatically to tasks and apply.

### 4. Tasks

- Break work into small, verifiable tasks with exact paths.
- Maintain the generated `openspec/changes/<change-name>/tasks.md` as the
  durable roadmap; do not create `apply-progress.md` for OpenSpec changes.
- Mark only genuinely independent work as `[P]`.
- Link implementation tasks to user stories and requirements (`[US<n>]`).
- Put tests before implementation — rules/common/testing.md is not optional here.
- Add checkpoints between foundational work and user-story work.
- For native Task tools, include the task contract from `sdd-tasks.md`:
  roadmap, dependencies, paths, acceptance, verification, and receipt.
- Validate the durable roadmap before applying it with
  `python3 ~/.claude/scripts/validate-task-roadmap.py <tasks.md>`.

### 5. Apply

- Apply only after the proposal/spec/design are internally consistent and any
  required decision gate has passed, using the
  CLI instructions returned by OpenSpec. Use `/opsx:apply` only when the user
  explicitly invokes that workflow or the automatic CLI route is unavailable.
- `/opsx:apply <change-name>` activates the ignored
  `.claude/convergence.active` marker automatically through
  `UserPromptSubmit`; if the hook is unavailable, run
  `~/.claude/scripts/convergence-start.sh <change-name>` explicitly. Do not
  start implementation with a stale marker for another change.
- Work one task at a time and record evidence in the task checklist and the
  repository's receipts.
- Preserve unrelated changes.
- Do not weaken tests or quality gates to make a task appear complete.
- Keep iterating while the task is actionable; stop only when the task is
  genuinely blocked or requires a new human decision, not merely because the
  first implementation failed.

#### Failure and re-planning budget

- First failure: capture the exact command, output, hypothesis, and changed
  files; retry only after a root-cause adjustment.
- Second failure of the same task: stop implementation and propose one bounded
  re-decomposition into smaller tasks. Preserve completed/verified nodes and
  keep the original task as the parent record.
- A re-plan may not silently expand scope. Any new files, requirements, or
  external side effects require the same human gate as the original design.
- Allow at most one automatic re-decomposition per task. If it fails again,
  escalate instead of looping.
- Do not create more agents to hide a failed task; parallelism is valid only
  when file ownership and dependencies prove genuine independence.

### 6. Verify

- Run the smallest fresh commands that prove each requirement.
- Run `/opsx:verify` when that generated workflow is available, then run the
  project's native formatter, linter, type checker, test runner, and build as
  applicable.
- Use the project's own formatter, linter, type checker, test runner, build.
- Review the final diff for scope, secrets, debug code, TODOs, generated files,
  and migration safety.
- Record skipped checks with a reason; never imply they passed.
- Before the final response, write
  `.claude/convergence/<change-name>.receipt` with `CHANGE`, `STATUS: PASS`,
  `ACCEPTANCE: PASS`, `VERIFY_EXIT: 0`, and non-empty `EVIDENCE`. The Stop
  gate reruns the native test runner; the receipt is not a substitute for a
  fresh run.
- The legacy `checklist.md` is not part of the active OpenSpec workflow; use
  the generated change artifacts and `/opsx:verify` for the systematic pass.

## Convergence rule

There is no fixed maximum for `verify → diagnose → apply` when the approved
scope and requirements remain unchanged. Continue until every requirement,
acceptance scenario, task, and project-native verification gate has fresh
passing evidence. A failed test, failed `/opsx:verify`, incomplete task, or
unresolved acceptance criterion is a non-complete state; never archive it and
never report it as "good enough".

The bounded budget above limits repeating the same failed hypothesis. When it
is exhausted, preserve the verified work, re-plan or ask for the missing
decision/external change, and resume the convergence loop afterward. Escalation
is a pause in execution, not permission to declare success.

## Phase report

Every phase closes with the same five fields. The decision gates are where someone
decides whether to spend the next phase's work, and that decision needs a
scannable report — not the artifact re-read out loud.

| Field | Content |
|---|---|
| `status` | done / blocked / needs-decision |
| `executive_summary` | 2-3 sentences. What this phase settled |
| `artifacts` | Paths written or updated in this phase |
| `next_recommended` | The single next phase or action, not a menu |
| `risks` | What could still invalidate this, or "none identified" |

This is the one place the Response Length Contract yields: a gate report is
structured because someone is approving spend, not reading prose.

## Resuming

To continue an existing feature: read `openspec/changes/<change>/`, inspect
`proposal.md`, `specs/`, `design.md` when present, and `tasks.md`; then use the
next CLI artifact/apply instruction from `automatic-task-orchestrator`. Use a
native `/opsx:*` step only when that explicit fallback is selected. No agent is
needed merely to resume a change.

## Archiving

After `/opsx:verify` and the repository's verification gates pass, archive the
change with `/opsx:archive`. OpenSpec owns the archive layout; do not move
change folders manually.
